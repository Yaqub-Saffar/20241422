# Skill v1 · 设计思路

## 这一版要解决的问题

Phase 1 手工完成第二周预习报告时暴露的问题，就是 v1 的设计目标：
**把手工写作时"靠临场判断"的部分，固化成可重复执行的规则。**

## 从手工版反推出的规则

下面每条都能在 `handmade/homework1.md` 里找到出处，不是凭空设计的。

| v1 的规则 | 手工版里的依据 |
| --- | --- |
| 五章骨架固定、不可增删 | 手工版五章齐全，顺序为 学习内容 → AI 总结 → 反思 → 实践 → 参考资料 + 思维导图，与老师模板一致 |
| 总结必须用 `>` 引用块 + `**加粗小标题：**` | 手工版 L24-26 全部使用该写法，是本人自发形成的稳定习惯 |
| 反思必须「不足」+「我的补充」两级 | 手工版 L39-42 明确分两级，且「我的补充」写了教材没提的 `\0` 截断问题 |
| 实践问题格式：出现环境 / 解决过程 / 经验总结 | 手工版 L48-66 三个小标题固定，解决过程是编号步骤 |
| 解决过程必须保留失败尝试 | 手工版 L52-55 记录了 4 步，其中 3 步是失败与排查（`cl` 找不到、`vcvars64.bat` 找不到、`LNK1168` 权限错误） |
| 思维导图三大分支 教材/课件/实践 | 手工版 L108-139 导图根节点与三分支完全一致 |
| 重点小节号原样保留 | 手工版 L9「第三章重点：3.4，3.5，特别 3.4.4」，这种精确到小节的要求必须逐字保留 |
| 参考资料分三类 | 手工版 L72-84 分 AI 工具 / 图书 / 网站三节 |

## 五个铁律的由来

铁律不是"模型不听话所以骂它"，而是对应三类具体的作弊风险：

1. **禁止编造** —— 教材正文在微信读书付费墙内，agent 读不到，只能靠公开资料猜。
   不设约束必然出现"听起来很像教材内容"的编造段落。
2. **实践经历零虚构** —— 报告是老师逐份评分的，编造的经历一旦在口头复核里露馅，
   整份报告的可信度都受影响。这一条同时保护学生自己。
3. **反思必须由用户作答** —— 「我的补充」是 2 分里最看重的部分，
   如果由 AI 自己编，这 2 分等于白拿，而且违背老师设这道题的目的。
4. **教材正文读不到** —— 把技术前提写进规则，避免后续版本反复踩同一个坑。
5. **版本与署名固定** —— 章节号写错是低级错误，规则化最省事。

## 关键设计选择

### 判断归模型，规则归脚本

- **交给模型判断**：内容总结、反思候选点的提出、思维导图的节点选择 —— 这些需要理解教材语义
- **交给脚本**：Mermaid 渲染、Markdown 转 HTML/PDF、文件命名与版本号推断 —— 这些必须每次完全一致

`tools/export.ps1` 就是"规则归脚本"的部分：渲染与导出是确定性任务，
写进 Skill 的自然语言指令里只会每次生成不一样的结果。

### 渐进式披露

SKILL.md 正文只保留流程与铁律（约 130 行），把以下内容拆出去按需读取：

- `references/structure.md` —— 完整骨架与分值
- `references/style.md` —— 文风细则
- `references/weekly-input-template.md` —— 输入模板

理由：这些是"写的时候才需要"的细节，放在正文里只会挤占上下文预算。

### 踩坑点章节

按《图解Skill》书中的说法，Anthropic 内部几百个技能的实践表明，
一个技能里信息密度最高的部分往往不是流程说明，而是踩坑点。
v1 的 6 条踩坑点全部来自手工版的实际写作障碍，后续每次迭代发现新问题就往这里追加。

## 已知不足（留给后续版本）

| 不足 | 计划在哪个版本解决 |
| --- | --- |
| 没有教材术语表，遇到"分组密码工作模式"这类概念时用词可能不统一 | v3 或 v4（对应评分细则「处理教材特定概念/术语」） |
| 没有可判对错的自动检查项，全靠阶段 3 的人工清单 | v4 或 v5（对应「引入自我检查/验证机制」） |
| 思维导图节点数、字数限制是硬性数字，遇到复杂章节会不够用 | v5（对应「处理边界情况或复杂章节」） |
| 版本号 N 靠推断 `output/` 目录，目录被手动改动时会错 | v6（对应「泛化能力或稳定性」） |
| 没有历史版本的质量对比数据，无法量化进化幅度 | v7 配套（对应「终版与 v1 对比」） |

## 本版验证方式

用第三周预习报告作为第一个测试样本：

- 输入：第三周学习内容（两本书的章节 + 每节内容提要）+ 两个真实实践问题
- 预期：`output/v1/generated.md` 结构完整、无空话、实践部分与用户输入逐条对应
- 人工审阅后写入 `output/v1/human-edited.md`，批注即为 v1 → v2 的改进依据
