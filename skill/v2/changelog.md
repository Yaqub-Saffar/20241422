## 触发变更的问题

v1 第一次实战（第三周报告）暴露了一类问题，而且**7 处人工批注里有 6 处是同一类**：

| 批注 | AI 原话 | 问题 |
| --- | --- | --- |
| L25 | 五种工作模式「串成密文链」 | 一句话覆盖五个并列项 |
| L25 | 「按 PKCS#7 等标准补齐」 | 只给标准名，没给规则 |
| L25 | 三个 EVP 函数「的分工」 | 只说职责，不说调用时机与失败语义 |
| L40 | 「泄露明文前缀的相等关系」 | 泄露范围笼统 |
| L41 | 「后果比 CBC 更严重」 | 悬空比较 |
| L55 | 「将不会加密剩余数据」 | 漏了"返回错误"这个失败语义 |
| L66 | 「AI 有明确的权限边界」 | 结论停在现象 |

v1 的自查清单 8 条里有 7 条在查**结构**（章节齐不齐、格式对不对），
结构合规和内容够细是两件事，所以这 7 条一处都没被拦住。

## 根因与对策

### 根因 1 · 把精度当成事后检查项 → 新增阶段 1.5

v1 的流程是「阶段 2 起草 → 阶段 3 自查」。但"够不够细"没有客观标准，
事后只能凭感觉判断——**等于把一个需要事前约束的问题交给了事后判断**。

v2 在阶段 1 与阶段 2 之间插入 **阶段 1.5 定精度**：
起草前对每个知识点写下「必须回答什么」，答案只能来自用户输入或已查到的来源，
**填不出就标 `⚠️待核实`，不许含糊带过**。清单保留到自查阶段逐条比对。

| 知识点类型 | 必须回答 |
| --- | --- |
| 并列概念 | 每个各自解决什么问题、机制差别、什么场景选它 |
| 抽象名词 | 具体规则是什么 + 一个例子或数字 |
| API | 调用时机、输入输出、**失败返回什么** |
| 数值 | 具体数字 + 出处 |
| 命令/编译选项 | 完整写法 + 出处 |

### 根因 2 · 缺一条能拦住"抽象名词"的硬规则 → 新增铁律 6

v1 的踩坑点 1 说「每段至少给出一个具体的机制」——"至少一个"太松，
一段话覆盖五个并列模式、只给一个机制，按 v1 规则算达标。

v2 收紧为两条：

- **铁律 6**：抽象名词（标准/规范/机制/算法/模式/原理）后面必须紧跟具体规则、参数、数量或数据
- **踩坑点 1**：「每段至少一个」→「**并列概念每个各给一个**，不许一句话打包」

### 补充：失败分支（踩坑点 3）

v1 的事实核查要求查函数名、参数、默认值、编译选项，漏了一类：**失败分支与返回值语义**。
v2 在阶段 1 明确要求查 `RETURN VALUES` 段，并给出理由：
「不做任何处理」和「返回错误」在源码里是两行不同的代码，对调用方意义完全不同。

### 补充：结论深度（踩坑点 9）

v1 要求"经验总结是结论性一句话"，但没说结论要下到多深，
AI 就停在最省力的抽象层。v2 要求下到**根本原因或能力边界**，并给了正反例。

## 为什么新增独立文件而不是塞进 style.md

`style.md` 管"怎么写句子"（句式、术语、报错格式、导图规范），
本轮要修的是"写什么颗粒度"。两者混在一起，`style.md` 会膨胀到 200 行以上，
而 SKILL.md 的渐进式披露原则是**按需读取**——起草前只需要读精度那一块。

放进独立文件后，SKILL.md 里只需一句「起草前必读 `precision.md`」，
模型在写总结段落时才会去加载它。

## 验证方法

同一份 `input/week03.md` 跑 v2，与 `output/v1/generated.md` 做 diff，
只检查 `feedback/v1-to-v2.md` 第五节列的那 7 个位置：

- 五个工作模式是否各自有独立说明
- PKCS#7 是否给出补齐规则
- 三个 EVP 函数是否写清调用时机与缓冲区大小
- IV 复用的泄露范围是否具体
- CTR 与 CBC 的对比是否点名、说了后果
- 关闭填充后 `EVP_EncryptFinal_ex` 是否提到返回错误
- 授权失败的结论是否下到能力边界

**判定：这 7 处都不需要人工再改，v2 才算有效。**
只改掉 3-4 处说明约束还不够紧，要继续收。
