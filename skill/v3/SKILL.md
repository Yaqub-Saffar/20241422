# 密码系统设计 · 预习报告生成

## 铁律（违反即作废，不许商量）

1. **禁止编造**。学习内容、教材知识点、报错信息、命令、文件路径、耗时、数据，只能来自两处：用户本轮的输入，或本次实际查到的公开来源。两者都没有时，写成 `⚠️待核实：<一句话>` 交用户确认，**不许凭印象补全**。
   - 注意边界：`⚠️待核实` **只用于"提纲要求了、但查不到"的地方**。提纲没要求的内容，见铁律 7。
2. **实践经历零虚构**。「实践问题与解决」章节里的每一个问题、每一条报错、每一步操作，都必须能对应到用户亲口提供的记录。用户没给就停下来问，**不许编一个"合理的"问题**。
3. **反思必须由用户作答**。不许自己编"我的补充"。先列出 3-5 个「AI 总结可能遗漏或有误」的候选点，逐个问用户，用户回答后再成文。
4. **教材正文读不到**。《Head First C》《Windows C/C++加密解密实战》正文在微信读书付费墙内。凡用户未提供的内容提要，不得凭空扩写教材细节。
5. **版本与署名固定**。标题写 `## 第N周预习报告`；思维导图根节点写 `((密码系统设计第N周))`；不写学号姓名（由用户在文件名体现）。
6. **抽象名词必须落地**（v2 新增）。正文里出现「标准」「规范」「机制」「算法」「模式」「原理」这类词时，**必须紧跟具体内容**——具体规则、具体参数、具体数量、具体数据。写不出具体内容，说明这部分没读懂或没查到：要么去查，要么标 `⚠️待核实`，**不许含糊带过**。
   - 反例：「不足时需要按 PKCS#7 标准补齐」——读者仍不知道要补几个字节。
   - 正例：「按 PKCS#7 补齐：需补 b 个字节（1 ≤ b ≤ 块大小）则追加 b 个值为 b 的字节；明文已是整数倍时额外补一整块。」
7. **不越出提纲范围**（v3 新增）。**只写输入提纲与用户要求覆盖的内容**。自己扩写、又查不到来源的，**整句删除**，不许挂 `⚠️待核实` 占位。
   - v2 反例：4.2 只要求说明各模式机制，AI 却自行加了「选型指引」，查不到后挂了个 `⚠️待核实`。
   - 口诀：**提纲没要求的，不写；写了的，必须有来源。**
8. **断言必须带条件**（v3 新增）。出现「必须」「一定」「都要」「不能」「总是」这类断言时，**必须能指出它成立的条件**；说不出条件，就改用带限定词的表述（「通常」「一般情况下」「在本例中」）。
   - v2 反例：「`impl` 参数必须传 NULL」——实际传 NULL 只是"用默认实现"，并非硬性要求。
   - v2 反例：「要求 `inl` 是块大小的整数倍」——抹掉了"仅对某类接口"这个前提。

## 六阶段流程

### 阶段 0 · 收集输入（不可跳过）

先检查仓库里是否已有 `input/weekNN.md`：有就直接读，**不要重复提问**。没有则按下列清单逐项问用户，拿到答案后写入 `input/weekNN.md`（模板见 `references/weekly-input-template.md`）：

- 本周是第几周？
- 学习内容：书名 + 章节号 + 重点小节 + **每节讲了什么**（这段最关键，只有章节号会让后面全靠编）
- 老师本周有无额外要求（指定 AI 工具、字数、格式变化等）？默认无
- 本周实际做了什么？遇到了什么报错？哪怕是"跟着敲代码报了个错"这种小事也要说
- 提交格式：默认为 `Markdown + PDF`

确定本轮版本号 N：取 `output/` 下已存在的最大版本号 +1；若 `output/` 为空则 N = 1。

### 阶段 1 · 事实核查

对本轮涉及的每个技术概念，优先 `websearch` / `webfetch` 查**官方一手来源**：

- OpenSSL / GmSSL 官网文档、头文件 API 说明
- 书籍在豆瓣 / ituring / 微信读书的**目录页**（只能确认章节标题，不能当正文用）
- GNU 工具官方手册（make、gcc）

规则：

- 涉及**版本号、函数名、参数、默认值、编译选项**时必须查到来源，不许凭记忆
- 涉及 **API 行为**时，除了成功路径，**必须查失败分支与返回值语义**（v2 新增）。
  「不做任何处理」和「返回错误」是两回事：前者调用方可以忽略返回值，后者必须处理。
  查手册时直接找 NOTES / RETURN VALUES 段，不要只读 SYNOPSIS。
- **查到的结论若要写成"必须/一定"（铁律 8），须连同它成立的条件一起记下来**（v3 新增）
- 查不到来源又不在用户输入里的 → 先按铁律 7 判断是否该写：提纲要求了才标 `⚠️待核实`，没要求就删
- 所有查过的来源记入「参考资料 · 网站」一节，带真实访问过的链接

### 阶段 1.5 · 定精度（v2 新增，不可跳过）

**为什么要有这一步**：v1 把精度当事后检查项，但"够不够细"没有客观标准，事后只能凭感觉。
本阶段把精度从**事后判断**改成**事前约束**——起草前先想清楚每个知识点要回答哪些问题。

对阶段 0 拿到的每个知识点，逐条写下「必须回答什么」，并当场填答案。
答案只能来自用户输入或阶段 1 查到的来源；**填不出就写 `⚠️待核实`**，不许含糊带过。

| 知识点类型 | 必须回答的问题 |
| --- | --- |
| **并列概念**（多个算法/模式/参数/工具） | 每个各自：解决什么问题？机制差别在哪？什么场景选它？<br>**禁止用一句话覆盖多个并列项** |
| **抽象名词**（标准/规范/机制/原理） | 具体规则是什么？给一个具体例子或数字 |
| **API / 函数** | 什么时候调用？输入输出是什么？**失败时返回什么**？ |
| **数值**（默认值、缓冲区大小、块长度、超时） | 具体数字 + 出处链接 |
| **命令 / 编译选项** | 完整写法（含所有必需参数）+ 出处 |

起草时的用法：写每一段之前，先在清单里找到对应条目，
**能指着清单说出「这一句在回答第几问」再落笔**。清单里没有的，说明是自己在发挥——
按铁律 7，**直接删掉**（若确属提纲要求又查不到，才标 `⚠️待核实`）。

清单本身不进入报告，但**要保留到自查阶段**（见阶段 3 第 9 条）。

对照的好/坏例子见 `references/precision.md`。

### 阶段 2 · 起草

严格按 `references/structure.md` 的五章骨架，顺序与标题不可增删。各节要求：

- **AI 总结**：用 `>` 引用块，段内以 `**加粗小标题：**` 引导，2-3 段。必须是"读过的内容"的转述，不是评价。
  **执行铁律 6**：每个并列概念各给一个机制，不许一句话打包。
- **反思与补充**：先执行铁律 3，再成文。必须同时包含 `- **AI 总结的不足**：` 与 `- **我的补充**：`；
  `我的补充` 至少有一条是教材里没写、只有用户知道的。涉及安全后果时要具体到
  **泄露什么、泄露多少、攻击者需要什么前提**，不许只说"不安全"。
- **实践问题与解决**：只结构化用户给的真实经历，格式为「`#### 问题 N：<一句话结论>` + `- **出现环境**：` + `- **解决过程**：`（编号步骤）+ `- **经验总结`：」。问题多于 2 个时取最真实的 2 个。解决过程要保留 1-2 处失败尝试，不许写成一次就对。
  **经验总结要下到根本原因或能力边界**（v2 新增）：不许停在现象复述。
  - 停在现象：「AI 智能体有明确的权限边界。」——正确但没有信息量。
  - 下到根因：「设备授权需要终端与网页交互，这是 AI 无法直接完成的环节，不是权限配置问题。」
- **参考资料**：分「AI 工具 / 图书 / 网站」三个小节，如实列出**本轮实际用过**的 AI 工具。
- **思维导图**：`mermaid mindmap` 代码块，根节点 `((密码系统设计第N周))`，固定三大分支 `教材` / `课件` / `实践`；教材分支先写「书名 第N章」再拆要点；每层 3-5 个节点，节点文案不超过 12 字。

文风细则见 `references/style.md`，精度标准见 `references/precision.md`。

输出到 `output/vN/generated.md`。

### 阶段 3 · 自查

前 8 条查**结构**，后 5 条查**语义精度与自洽**（v2 新增 4 条 + v3 新增 1 条）。两类都要过。

- [ ] 五个章节齐全、顺序与标题与 `structure.md` 完全一致
- [ ] 全文已无 `⚠️待核实` 残留（或已列出待用户确认项）
- [ ] 「实践问题」每一条都能追溯到用户输入
- [ ] 「我的补充」是第一人称真实观点，不是 AI 总结的复述
- [ ] 解决过程保留了失败尝试，不是流水账一次成功
- [ ] 思维导图是 `mindmap`、根节点正确、三大分支齐全、节点字数达标
- [ ] 参考资料三类齐全，链接真实访问过
- [ ] 全文无「随着科技的飞速发展」「综上所述」「在当今社会」这类空话
- [ ] **（精度）** 文中每个并列项是否各自有独立说明，没有被一句话打包
- [ ] **（精度）** 文中每个 API 是否都写清了调用时机，且**失败分支**与返回值语义明确
- [ ] **（精度）** 全文是否还有只给名字不给内容的抽象名词（"按标准""采用机制""原理是"）
- [ ] **（精度）** 逐条比对阶段 1.5 的清单：报告里每段都能对上清单里的某一问，没有清单外的自由发挥
- [ ] **（自洽，v3 新增）** 同一概念在全文中的表述前后一致，无自相矛盾（例：不能前面说"IV 不必保密"、后面说"要求 IV 保密"）

自查不通过就先改，改完再交给用户。

### 阶段 3.5 · 标薄弱点（v3 新增，不可跳过）

**为什么要有这一步**：v2 的产物很详实，但**通篇语气一样自信**，人审阅时分不清
哪句查证过、哪句是推的，导致"AI 用笃定口吻写错的地方"要靠人逐句去找。
本阶段让 AI 在自己没把握的地方**主动举手**。

1. **逐段打置信度**：对每一段，按 `references/review-anchors.md` 的三级（高/中/低）判断。
   口诀：**"这句话我能点出出处吗？"** 点不出的，至少是"中"。
2. **在"中/低"处插入锚点**：紧贴可疑句写 HTML 注释
   `<!-- 待确认：<我为什么举手> + <需要确认什么> -->`。
3. **产出 `output/vN/self-review.md`**：把全部锚点汇总成表（位置 / 置信度 / 待确认什么 / 建议），
   与正文锚点**一一对应**。模板见 `references/review-anchors.md`。

锚点与清单**只用于"中/低"置信度**，不许为了显得严谨而滥标。

### 阶段 4 · 导出

```powershell
powershell -ExecutionPolicy Bypass -File tools\export.ps1 -Report output\vN\generated.md
```

产出 `output/vN/generated.pdf`，思维导图 PNG 落在 `assets/`。DOCX 默认不生成。

导出后**必须提醒用户**：
1. 草稿不能直接交，需人工逐句审阅，另存为 `output/vN/human-edited.md`，并在每处改动旁用 `[[修改原因]]` 标注。这些批注是评分的硬性证据。
2. **优先看 `output/vN/self-review.md` 的待确认项**——锚点已把"我没把握的地方"挑出来了。

## 踩坑点

以下每一条都来自实际写作暴露的问题，生成时逐条自查：

1. **总结写成概念罗列，且并列项被一句话打包**。v1 的下限是「每段至少给出一个具体机制」，
   于是"讲了五个工作模式、只给一个机制"也算达标，读者依然不知道另外四个的区别。
   → **并列概念每个各给一个机制**，并说清各自解决什么问题、什么时候用。
2. **抽象名词当内容用**。「按标准补齐」「采用标准填充」——给了名字没给规则。
   → 执行铁律 6，抽象名词后面必须跟具体规则或数字。
3. **API 只写成功路径**。「不会加密剩余数据」听起来像静默跳过，实际是返回错误。
   → 涉及 API 必须查 RETURN VALUES / 失败分支。
4. **「我的补充」变成复述**。AI 把自己刚写的总结换个说法再写一遍。→ 补充里必须出现教材没写、用户才知道的东西。
5. **解决过程编得太顺**。真实过程有弯路。→ 保留 1-2 处失败尝试（报错 → 排查 → 换思路）。
6. **思维导图摊平成一堆平级节点**。→ 守住 教材 / 课件 / 实践 三大分支。
7. **重点小节号漏抄**。用户给的「4.2、4.3、4.5」这类重点编号必须原样出现在「学习内容」里。
8. **章节号写错**。第 3 周写成「第4周」这类错误，检查标题与导图根节点是否一致。
9. **经验总结停在现象**。「有权限边界」「需要授权」这类话谁都能说，等于没说。
   → 追问一句：根本原因是配置错了，还是这件事本身 AI 就做不到？后者才值得写。
10. **越出提纲范围就挂占位**（v3 新增）。提纲没要求的内容自己加戏，查不到就挂 `⚠️待核实`
    搪塞，等于把"编造"换成了"免责声明"。→ 执行铁律 7，整句删除。
11. **把有前提的结论写成绝对断言**（v3 新增）。「必须传 NULL」「要求整数倍」抹掉了前提。
    → 执行铁律 8，能说条件才用绝对词，否则加限定词。
12. **前后自相矛盾**（v3 新增）。同一节里前句"不必保密"、后句"必须保密"。→ 执行自查自洽项。

## 禁止清单

- 不许写「随着科技的飞速发展」「综上所述」「在当今社会」「相信随着技术进步」等空话
- 不许编造用户没提过的报错信息、命令、文件路径、环境版本
- 不许编造教材正文内容
- 不许把「AI 总结」写成自己的阅读体会，两节必须分开
- 不许用「我」描述 AI 的行为，也不许让 AI 假装成用户第一人称写实践经历
- 不许省略「参考资料 · AI 工具」一栏
- 不许改动五章骨架的标题与顺序
- 不许输出思维导图以外的图形（不使用 graphviz / plantuml）
- **不许用一句话覆盖多个并列概念**（v2）
- **不许只写 API 的职责而不写调用时机与失败语义**（v2）
- **不许跳过阶段 1.5 直接起草**（v2）
- **不许对提纲没要求的内容挂 `⚠️待核实` 占位**（v3）
- **不许用「必须/一定/都要/不能」写说不出成立条件的断言**（v3）
