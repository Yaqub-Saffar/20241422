# 密码系统设计 · 预习报告生成

## 铁律（违反即作废，不许商量）

1. **禁止编造**。学习内容、教材知识点、报错信息、命令、文件路径、耗时、数据，只能来自两处：用户本轮的输入，或本次实际查到的公开来源。两者都没有时，写成 `⚠️待核实：<一句话>` 交用户确认，**不许凭印象补全**。
   - 注意边界：`⚠️待核实` **只用于"提纲要求了、但查不到"的地方**。提纲没要求的内容，见铁律 7。
2. **实践经历零虚构**。「实践问题与解决」章节里的每一个问题、每一条报错、每一步操作，都必须能对应到用户亲口提供的记录。用户没给就停下来问，**不许编一个"合理的"问题**。
3. **反思必须由用户作答**。不许自己编"我的补充"。先列出 3-5 个「AI 总结可能遗漏或有误」的候选点，逐个问用户，用户回答后再成文。
4. **教材正文读不到**。《Head First C》《Windows C/C++加密解密实战》正文在微信读书付费墙内。凡用户未提供的内容提要，不得凭空扩写教材细节。
5. **版本与署名固定**。标题写 `## 第N周预习报告`；思维导图根节点写 `((密码系统设计第N周))`；不写学号姓名（由用户在文件名体现）。
6. **抽象名词必须落地**（v2 新增）。正文里出现「标准」「规范」「机制」「算法」「模式」「原理」这类词时，**必须紧跟具体内容**——具体规则、具体参数、具体数量、具体数据。写不出具体内容，说明这部分没读懂或没查到：要么去查，要么标 `⚠️待核实`，**不许含糊带过**。
   - 反例：「不足时需要按 PKCS#7 标准补齐」——读者仍不知道要补几个字节。
   - 正例：「按 PKCS#7 补齐：需补 b 个字节（1 ≤ b ≤ 块大小）则追加 b 个值为 b 的字节；明文已是整数倍时额外补一整块。」
7. **不越出提纲范围**（v3 新增）。**只写输入提纲与用户要求覆盖的内容**。自己扩写、又查不到来源的，**整句删除**，不许挂 `⚠️待核实` 占位。
   - v2 反例：4.2 只要求说明各模式机制，AI 却自行加了「选型指引」，查不到后挂了个 `⚠️待核实`。
   - 口诀：**提纲没要求的，不写；写了的，必须有来源。**
8. **断言必须带条件**（v3 新增）。出现「必须」「一定」「都要」「不能」「总是」这类断言时，**必须能指出它成立的条件**；说不出条件，就改用带限定词的表述（「通常」「一般情况下」「在本例中」）。
   - v2 反例：「`impl` 参数必须传 NULL」——实际传 NULL 只是"用默认实现"，并非硬性要求。
   - v2 反例：「要求 `inl` 是块大小的整数倍」——抹掉了"仅对某类接口"这个前提。
9. **术语全课程统一**（v4 新增）。同一个概念在全课程用同一个写法；术语**首次出现给中英对照**，缩写在首次出现时给全称。以 `references/glossary.md` 为准，词表里没有的新词当场补录。涉及法律法规与标准名称时以 `references/standards.md` 为准。
   - v3 反例：`OAEP` 首次出现只写了缩写，没给全称；`provider` 没给中英对照。
10. **导出前必过机检**（v5 新增）。草稿完成后**必须**跑 `tools/check-report.ps1`，**全部 PASS 才能进阶段 4 导出**；有 FAIL 先修，不许带 FAIL 交付。机检判不了的部分（语义）见阶段 3 人检项。
    - v4 反例：14 条自查全靠记性，锚点数与 `self-review.md` 行数是否一致、导图节点是否超长，都要人肉核对。
11. **复杂章节先分流再写**（v6 新增）。命中「复杂章节」条件（一本书 ≥3 个重点小节 / 一周跨两本书 / 某节并列概念 ≥4 个）时，**必须**按 `references/complex-chapter.md` 组织：长章节总结按小节号分组、导图教材分支按"书名 章"分层。**导图超限时，调 `report.config.yml` 阈值或合并同类节点，并在 `self-review.md` 里报备**，不许悄悄摊平。
    - v5 反例：第9章+第7章内容偏多时，导图「教材」分支一路摊平到 5 个二级节点，读者看不出两本书的分界。
12. **版本号与配置必须显式、可校验**（v7 新增）。版本号 N 用 `tools/version.ps1` 按「命令行 → front-matter → 推断」的优先级确定，**推断时必须提示**；`report.config.yml` 的非法值/未知键由 `check-report.ps1` **报警并回退默认**，不许静默生效或静默忽略。
    - v6 反例：`max_node_chars: abc` 被静默解析成 0（所有节点"超长"），拼错的 `max_childern` 被静默忽略。

## 六阶段流程

### 阶段 0 · 收集输入（不可跳过）

先检查仓库里是否已有 `input/weekNN.md`：有就直接读，**不要重复提问**。没有则按下列清单逐项问用户，拿到答案后写入 `input/weekNN.md`（模板见 `references/weekly-input-template.md`）：

- 本周是第几周？（这是**课程周次**，不是 Skill 版本号）
- 学习内容：书名 + 章节号 + 重点小节 + **每节讲了什么**（这段最关键，只有章节号会让后面全靠编）
- 老师本周有无额外要求（指定 AI 工具、字数、格式变化等）？默认无
- 本周实际做了什么？遇到了什么报错？哪怕是"跟着敲代码报了个错"这种小事也要说
- 提交格式：默认为 `Markdown + PDF`

**确定 Skill 版本号 N（v7 起显式解析）**：

```powershell
powershell -ExecutionPolicy Bypass -File tools\version.ps1 -Input input\weekNN.md
```

优先级：命令行 `-Version` → 输入 front-matter 的 `report_version:` → 推断 `output\` 最大版本号 +1。
**若输出提示"推断值"，先与用户确认再继续**；能被显式指定的，不要靠推断。

读 `report.config.yml`（仓库根目录）：本周的导图节点字数/分支数/层数上限、总结是否按小节号分组，都以它为准；文件不存在就用内置默认。**配置写坏了 `check-report.ps1` 会报警**（见阶段 3A）。

### 阶段 1 · 事实核查

对本轮涉及的每个技术概念，优先 `websearch` / `webfetch` 查**官方一手来源**：

- OpenSSL / GmSSL 官网文档、头文件 API 说明
- 书籍在豆瓣 / ituring / 微信读书的**目录页**（只能确认章节标题，不能当正文用）
- GNU 工具官方手册（make、gcc）

规则：

- 涉及**版本号、函数名、参数、默认值、编译选项**时必须查到来源，不许凭记忆
- 涉及 **API 行为**时，除了成功路径，**必须查失败分支与返回值语义**（v2 新增）。
  「不做任何处理」和「返回错误」是两回事：前者调用方可以忽略返回值，后者必须处理。
  查手册时直接找 NOTES / RETURN VALUES 段，不要只读 SYNOPSIS。
- **查到的结论若要写成"必须/一定"（铁律 8），须连同它成立的条件一起记下来**（v3 新增）
- 查不到来源又不在用户输入里的 → 先按铁律 7 判断是否该写：提纲要求了才标 `⚠️待核实`，没要求就删
- 所有查过的来源记入「参考资料 · 网站」一节，带真实访问过的链接

### 阶段 1.5 · 定精度（v2 新增，不可跳过）

**为什么要有这一步**：v1 把精度当事后检查项，但"够不够细"没有客观标准，事后只能凭感觉。
本阶段把精度从**事后判断**改成**事前约束**——起草前先想清楚每个知识点要回答哪些问题。

对阶段 0 拿到的每个知识点，逐条写下「必须回答什么」，并当场填答案。
答案只能来自用户输入或阶段 1 查到的来源；**填不出就写 `⚠️待核实`**，不许含糊带过。

| 知识点类型 | 必须回答的问题 |
| --- | --- |
| **并列概念**（多个算法/模式/参数/工具） | 每个各自：解决什么问题？机制差别在哪？什么场景选它？<br>**禁止用一句话覆盖多个并列项** |
| **抽象名词**（标准/规范/机制/原理） | 具体规则是什么？给一个具体例子或数字 |
| **API / 函数** | 什么时候调用？输入输出是什么？**失败时返回什么**？ |
| **数值**（默认值、缓冲区大小、块长度、超时） | 具体数字 + 出处链接 |
| **命令 / 编译选项** | 完整写法（含所有必需参数）+ 出处 |

起草时的用法：写每一段之前，先在清单里找到对应条目，
**能指着清单说出「这一句在回答第几问」再落笔**。清单里没有的，说明是自己在发挥——
按铁律 7，**直接删掉**（若确属提纲要求又查不到，才标 `⚠️待核实`）。

清单本身不进入报告，但**要保留到自查阶段**。

对照的好/坏例子见 `references/precision.md`。

### 阶段 1.6 · 术语对齐（v4 新增，不可跳过）

1. 打开 `references/glossary.md`，对本周涉及的**每一个概念**查词表：
   - 词表里有 → 记下「统一写法」与「首次出现规范」；
   - 词表里没有 → **当场补录一行**（统一写法 + 首次出现规范 + 别名），再往下走。
2. 涉及法律法规、国家标准、NIST 标准的名称与标准号 → 以 `references/standards.md` 为准。
3. 把本周要用的术语定名清单保留到自查阶段。

### 阶段 2 · 起草

严格按 `references/structure.md` 的五章骨架，顺序与标题不可增删。各节要求：

- **AI 总结**：用 `>` 引用块，段内以 `**加粗小标题：**` 引导，2-3 段。必须是"读过的内容"的转述，不是评价。
  **执行铁律 6**：每个并列概念各给一个机制，不许一句话打包。**执行铁律 9**：术语按阶段 1.6 定名，首现给中英对照。
- **反思与补充**：先执行铁律 3，再成文。必须同时包含 `- **AI 总结的不足**：` 与 `- **我的补充**：`；
  `我的补充` 至少有一条是教材里没写、只有用户知道的。涉及安全后果时要具体到
  **泄露什么、泄露多少、攻击者需要什么前提**，不许只说"不安全"。
- **实践问题与解决**：只结构化用户给的真实经历，格式为「`#### 问题 N：<一句话结论>` + `- **出现环境**：` + `- **解决过程**：`（编号步骤）+ `- **经验总结**：`」。问题多于 2 个时取最真实的 2 个。解决过程要保留 1-2 处失败尝试，不许写成一次就对。
  **经验总结要下到根本原因或能力边界**（v2 新增）：不许停在现象复述。
  - 停在现象：「AI 智能体有明确的权限边界。」——正确但没有信息量。
  - 下到根因：「设备授权需要终端与网页交互，这是 AI 无法直接完成的环节，不是权限配置问题。」
- **参考资料**：分「AI 工具 / 图书 / 网站」三个小节，如实列出**本轮实际用过**的 AI 工具。
- **思维导图**：`mermaid mindmap` 代码块，根节点 `((密码系统设计第N周))`，固定三大分支 `教材` / `课件` / `实践`；
  教材分支先写「书名 第N章」再拆要点；节点数量/字数/层数遵守 `report.config.yml` 的上限。

#### 长章节组织（v6 新增）

写完草稿前先判断本周是否属于「复杂章节」（判据见 `references/complex-chapter.md`）：

- **一本书 ≥3 个重点小节** → 「AI 总结」按**小节号分组**（每组一个 `**7.2 …：**` 式小标题）；
- **一周跨两本书** → 导图「教材」分支**先按"书名 第N章"分层**，再列要点；
- **某节并列概念 ≥4 个** → 逐个成句（铁律 6），必要时拆成子组；
- **导图触顶**（节点字数/分支数/层数超 `report.config.yml` 上限）→ 先精简措辞，再合并同类到一层，
  或调 `report.config.yml` 放宽；**任何合并/放宽都在 `self-review.md` 报备一行**。

文风细则见 `references/style.md`，精度标准见 `references/precision.md`，术语见 `references/glossary.md`，
复杂章节写法见 `references/complex-chapter.md`。

输出到 `output/vN/generated.md`。

### 阶段 3 · 自查（机检 + 人检两道）

v5 起，自查拆成**机检**与**人检**两道，都要过。机检负责"格式结构一条不漏"，
人检负责"语义是否正确"，**别因为有了脚本就放松语义检查**。

#### 3A · 机检（必过，判不了语义）

**跑脚本**：

```powershell
powershell -ExecutionPolicy Bypass -File tools\check-report.ps1 -Report output\vN\generated.md
```

全部 PASS 才继续（脚本对 FAIL 项会定位到具体内容）。脚本覆盖 9 项：
五章标题与顺序 / 无 `⚠️待核实` 残留 / 导图根节点格式 / 导图节点字数 /
无空话黑名单 / 缩写首现带中英对照 / 锚点数 == `self-review.md` 行数 / 必备标题存在 /
**导图分支数与层数**（字数、分支数、层数的阈值**读 `report.config.yml`**，可用 `-Config` 指定）。

**v7 起会做配置校验**：非法值回退默认并打印 `[配置警告]`，未知键报警——
先看有没有配置警告，再看报告本身。

> ⚠️ 脚本是 `.ps1`，**PowerShell 5.1 要求带 UTF-8 BOM**，否则中文会被当 GBK 解析报错。
> 改动脚本后确认首三字节是 `EF BB BF`。

#### 3B · 人检（脚本判不了，逐条看）

- [ ] **（精度）** 文中每个并列项是否各自有独立说明，没有被一句话打包
- [ ] **（精度）** 文中每个 API 是否都写清了调用时机，且**失败分支**与返回值语义明确
- [ ] **（精度）** 全文是否还有只给名字不给内容的抽象名词（"按标准""采用机制""原理是"）
- [ ] **（精度）** 逐条比对阶段 1.5 的清单：报告里每段都能对上清单里的某一问，没有清单外的自由发挥
- [ ] **（自洽）** 同一概念在全文中的表述前后一致，无自相矛盾
- [ ] **（术语）** 本周术语是否都按 `glossary.md` 的统一写法，且首次出现带了中英对照 / 缩写全称
- [ ] **（结构）** 复杂章节是否按小节号分组、导图是否按"书名 章"分层、超限合并是否已报备（v6）
- [ ] **（实践）** 「实践问题」每一条都能追溯到用户输入；解决过程保留了失败尝试
- [ ] **（反思）** 「我的补充」是第一人称真实观点，不是 AI 总结的复述
- [ ] **（深度）** 经验总结下到根本原因或能力边界，不是现象复述

详见 `references/self-check.md`。

### 阶段 3.5 · 标薄弱点（v3 新增，不可跳过）

**为什么要有这一步**：v2 的产物很详实，但**通篇语气一样自信**，人审阅时分不清
哪句查证过、哪句是推的，导致"AI 用笃定口吻写错的地方"要靠人逐句去找。
本阶段让 AI 在自己没把握的地方**主动举手**。

1. **逐段打置信度**：对每一段，按 `references/review-anchors.md` 的三级（高/中/低）判断。
   口诀：**"这句话我能点出出处吗？"** 点不出的，至少是"中"。
2. **在"中/低"处插入锚点**：紧贴可疑句写 HTML 注释
   `<!-- 待确认：<我为什么举手> + <需要确认什么> -->`。
3. **产出 `output/vN/self-review.md`**：把全部锚点汇总成表（位置 / 置信度 / 待确认什么 / 建议），
   与正文锚点**一一对应**；若因导图触顶做过合并或放宽配置，**额外记一行报备**。
4. **改完锚点后，再跑一次机检**：确认第 7 项（锚点数 == 清单行数）仍然 PASS。

锚点与清单**只用于"中/低"置信度**，不许为了显得严谨而滥标。

### 阶段 4 · 导出

```powershell
powershell -ExecutionPolicy Bypass -File tools\export.ps1 -Report output\vN\generated.md
```

产出 `output/vN/generated.pdf`，思维导图 PNG 落在 `assets/`。DOCX 默认不生成。

人工定稿 `output/vN/human-edited.md` 后，可再跑一次机检（第 7 项改为**断言锚点已全部解除**）：

```powershell
powershell -ExecutionPolicy Bypass -File tools\check-report.ps1 -Report output\vN\human-edited.md -Week N -Final
```

导出后**必须提醒用户**：
1. 草稿不能直接交，需人工逐句审阅，另存为 `output/vN/human-edited.md`，并在每处改动旁用 `[[修改原因]]` 标注。这些批注是评分的硬性证据。
2. **优先看 `output/vN/self-review.md` 的待确认项**——锚点已把"我没把握的地方"挑出来了。
3. 若本周补录了新术语到 `glossary.md`，一并提示用户确认。

## 踩坑点

1. **总结写成概念罗列，且并列项被一句话打包**。→ **并列概念每个各给一个机制**。
2. **抽象名词当内容用**。「按标准补齐」「采用标准填充」——给了名字没给规则。→ 执行铁律 6。
3. **API 只写成功路径**。「不会加密剩余数据」听着像静默跳过，实际是返回错误。→ 查 RETURN VALUES。
4. **「我的补充」变成复述**。→ 补充里必须出现教材没写、用户才知道的东西。
5. **解决过程编得太顺**。→ 保留 1-2 处失败尝试。
6. **思维导图摊平成一堆平级节点**。→ 守住 教材 / 课件 / 实践 三大分支。
7. **重点小节号漏抄**。用户给的「4.2、4.3、4.5」必须原样出现在「学习内容」里。
8. **章节号写错**。第 3 周写成「第4周」这类错误，检查标题与导图根节点是否一致。
9. **经验总结停在现象**。→ 追问：根本原因是配置错了，还是这件事本身 AI 就做不到？
10. **越出提纲范围就挂占位**（v3）。→ 执行铁律 7，整句删除。
11. **把有前提的结论写成绝对断言**（v3）。→ 执行铁律 8。
12. **前后自相矛盾**（v3）。→ 执行人检自洽项。
13. **术语跨周不统一 / 首现不规范**（v4）。→ 执行阶段 1.6 与铁律 9。
14. **自查靠记性、漏检**（v5）。清单越长越依赖记性，人不会逐条勾。→ 执行铁律 10，跑机检脚本。
15. **复杂章节把导图摊平 / 总结变流水账**（v6）。→ 执行铁律 11，按小节号分组、按书分层；触顶就报备。
16. **版本号靠推断 / 配置写坏不报错**（v7）。→ 执行铁律 12，用 `version.ps1` 显式定版，看配置警告。
